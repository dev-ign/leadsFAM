# ADR 0013: Measured search performance

The first 1k/10k/50k run found five-second API timeouts for broad substring search at larger sizes. Lists, detail and timeline stayed usable. A 100-row import initially timed out too; explicitly chosen distinct contacts no longer perform an unnecessary duplicate search, bringing the measured sequential batch below one second.

A parameter-specific query plan avoids generic plans for optional filters. Parameters remain bound with `USING`; no caller text becomes SQL syntax. Existing function owners, ACLs, RLS, volatile session/membership checks and lock ordering are unchanged. See [PostgreSQL's EXECUTE documentation](https://www.postgresql.org/docs/17/plpgsql-statements.html#PLPGSQL-STATEMENTS-EXECUTING-DYN).

The database reports `starts_with` as leakproof, while `texticlike` is not. PostgreSQL may evaluate leakproof filters before RLS, while other filters follow policy checks; this is an intentional security boundary, not an optimizer defect. See [RLS evaluation rules](https://www.postgresql.org/docs/17/ddl-rowsecurity.html) and [SP-GiST index support](https://www.postgresql.org/docs/17/spgist.html).

Default search therefore uses case-normalized **prefixes** over generated name/title columns and existing normalized email/phone values. Native SP-GiST text indexes support prefix lookup; ordinary tenant predicates and per-row RLS still apply. Contact/lead candidates are unioned once inside PostgreSQL, rather than repeatedly searching channels for each lead. Generated search columns are derivative index data, excluded from application DTOs; clients cannot set them. No extension, service, authorization cache, leakproof reclassification or policy change is introduced.

An explicit `contains` mode retains bounded literal substring behavior and may time out on large organizations. The UI exposes both matching meanings. The cursor binds the mode along with every other query setting. Initial latency targets remain targets; final measurements and failures must be reported, including broad-prefix and substring limitations. This is a local engineering result, not a production SLA.

The candidate set is joined by tenant-safe UUID equality; an `IN` filter alone made the ordered result scan recheck many nonmatching contacts. Source filters likewise use a composite-key join. For `mine`/a specific assignee, the single target membership generation is resolved under the existing organization SHARE lock, then compared to historical row generation. That is a locked assignment value, not an authorization cache: every underlying relation keeps its original volatile per-row session/membership RLS. Unassigned filtering still checks each distinct historical target as needed.
