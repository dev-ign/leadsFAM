# ADR 0005: Server-owned Supabase sessions and recovery isolation

Status: selected before implementation; implemented and verified locally in Phase 01. LeadsFam retains the @leadops internal package scope. The approved local container gate must pass before authentication implementation.

## Alternatives and decision

| Architecture                                                   | Advantages                                                                                                                                                        | Costs / fit                                                                                                                                                                                                                               |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supported browser Supabase SDK with bearer tokens              | Least application session code; supported refresh; no ambient API cookies                                                                                         | JavaScript holds provider credentials; long-lived browser storage is unnecessary exposure for this product; recovery JWTs still need an independent database access boundary                                                              |
| Supported SSR cookie storage                                   | Existing SDK cookie adapter and refresh patterns                                                                                                                  | Standard examples share tokens with browser code. A server-only variant needs CSRF protection, concurrent refresh coordination, recovery isolation, and precise cookie/cache behavior. HttpOnly alone does not change database privileges |
| Encrypted token-bearing HttpOnly cookie                        | Avoids storing token ciphertext in a database                                                                                                                     | Requires encryption-key rotation, cookie-size limits, stale-cookie/parallel-refresh handling, and a database session/recovery registry anyway. A signed/encrypted cookie alone cannot provide immediate application revocation            |
| Opaque HttpOnly cookie plus private PostgreSQL session records | Provider tokens stay server-side; one shared refresh lock; explicit revocation, expiry and recovery purpose; database can require an enrolled application session | Adds token encryption, one database lookup, bounded refresh transactions, cleanup and key-management duties                                                                                                                               |

Choose the opaque-cookie design as the smallest complete fit for the selected server-owned credential and recovery policies. Opaque sessions are not required by Supabase Auth itself. They are justified here because the simpler alternatives still need a database registry and refresh coordination to meet these application policies. We use Supabase's supported Auth HTTP endpoints with a typed, runtime-validated adapter. Supabase still owns passwords, verification and token issuance. The pinned JS SDK failed strict TypeScript 6 compilation because its browser credential declarations conflict with DOM types; removing the unused SDK avoided weakening checks. No Redis, separate identity service or generic session framework is introduced.

The browser receives a random identifier only; its hash is stored. A dedicated non-superuser, NOBYPASSRLS login owns no tables and can access only the private session store / narrowly granted session enrollment operations. Normal tenant queries use the verified user's Supabase JWT and RLS, not the session-store role or service-role keys. Clients are request scoped. Cookie responses are private/no-store. Production uses host-only Secure/HttpOnly/SameSite cookies; unsafe requests, including login, require exact-origin and session-bound CSRF checks. Local HTTP exceptions are restricted to loopback development.

## Recovery is a database boundary

A Supabase recovery credential must be treated as potentially capable of producing an authenticated Supabase JWT. Merely marking a BFF cookie as recovery-only would leave a direct Data API bypass if RLS accepted every authenticated JWT.

Tenant policies and all organization mutation functions must additionally require an active application-purpose session enrollment keyed to the provider-verified user/session ID. Only trusted backend code may enroll a session after successful password sign-in; browser roles cannot enroll or edit it. Recovery sessions are recorded with recovery purpose and never satisfy this predicate. Direct recovery JWTs must fail ordinary tenant queries and RPCs as well as API requests. The recovery credential may only replace the password; completion revokes existing application sessions and requires a fresh sign-in. Expired, replayed, or wrong-purpose credentials fail closed. Actual provider-issued recovery tokens must be used in integration tests to verify these assumptions before 01B passes.

## Operational obligations

- Encrypt token material with authenticated encryption (AES-256-GCM), an explicit key ID and version, random nonce, and context-bound associated data. Never log plaintext, ciphertext, cookie values, passwords, OTPs or encryption keys.
- Accept an active encryption key plus a bounded previous-key set. New/rotated records use the active key; records read with a previous key are re-encrypted. Remove an old key only after migration/expiry. Missing/invalid keys deny the affected session; emergency retirement invalidates sessions and requires sign-in. Production keys must come from deployment secret management; generated local keys are never versioned.
- Enforce idle and absolute expiry at request authorization and in the database session predicate. Cleanup is maintenance, not the expiry security control. Run bounded deletion of expired/revoked records with an explicit retention policy; no new worker service is needed.
- Lock the session row across a bounded refresh operation, persist rotated credentials atomically and let competing requests reread the committed result. Network/database failures return safe unavailable/unauthorized states, never a privileged fallback. Lost responses or ambiguous refresh outcomes require conservative retry or reauthentication, not token reuse loops.
- Preserve a valid session on transient provider errors where safe, but do not authorize without the required verification. Logout removes local authority immediately; provider revocation failures are reported/audited safely and cannot restore local access.
- Test parallel refresh, process/request failure around refresh persistence, expiry, revoked sessions, key rotation, unreadable ciphertext, cleanup, and provider/database unavailability.

Authentication proves identity; current membership grants operation permission; RLS and tenant-aware constraints bound data. None can substitute for another. Membership revocation is checked again in database operations. In-flight operations must have a defined ordering against revocation using organization locks; already delivered data cannot be recalled.

Sources: [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [server-side advanced guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide), [getUser verification](https://supabase.com/docs/reference/javascript/auth-getuser). Documentation describes the SDK; the private session/enrollment layer is application code whose behavior requires its own tests.

## Implemented recovery fence and key procedure

A provider password change and a PostgreSQL transaction cannot be one atomic commit. Before changing the password, the server commits revocation of application sessions and a private `auth_guards.blocked` fence. A per-user advisory lock orders enrollment with recovery. Successful completion commits a new database timestamp and clears the fence; sign-ins that began before that timestamp cannot enroll. Failure leaves the fence blocked and permits a recovery retry. This deliberately prefers loss of availability over preserving possibly compromised access. Fresh password sign-in is required after completion. Ordinary users have no access to fence records.

For encryption rotation, distribute both old and new keys to **all** workers before selecting the new active key. Reads re-encrypt with the active key. Retain the old key until all sessions have rotated or their 12-hour absolute lifetime has expired; then remove it. A worker missing an envelope key fails closed and revokes that session. Lost keys require signing in again. No production key manager, deployment or backup system is configured in this local phase.

The implementation uses a fixed five-second timeout for each provider request, row locks for refresh, a runtime-role startup check, versioned AES-256-GCM envelopes bound to session hash/user/provider-session/purpose, and at most 500 expired/revoked deletions per minute per worker. Cleanup failures emit safe logs; cleanup is never the authorization boundary. A process/database failure after remote refresh can leave the old refresh token in storage; provider reuse behavior may allow recovery, otherwise the session is denied and fresh sign-in is required. No unverified token fallback is accepted.

HTTP reference: [official Auth OpenAPI](https://github.com/supabase/auth/blob/master/openapi.yaml). Only documented Auth user endpoints and named PostgREST RPCs are used; no admin Auth endpoint or service-role client is in the runtime.
