## Implementation plan

1. Reuse existing application sessions, CSRF, organization authorization, canonical contact normalization/validation, duplicate candidate matching, CRM constraints, activity history, tenant composite foreign keys and Phase 02F query policies. Human CRM authority remains unchanged.
2. Add private integration, ingestion receipt, event, workflow/version, run and job relations. All have RLS and bounded read APIs. Preserve receipt identity indefinitely. Add integration attribution to CRM records without impersonating members; existing human rows remain valid.
3. Human management uses current application JWT RPCs with Owner/Admin checks. A separate server-to-server intake endpoint accepts a random, expiring integration bearer credential; its hash resolves tenant/source and the only allowed operation, lead intake. Never put that credential in a website bundle. Create/rotate reveals it once. Pause/revoke take effect under the same organization lock as intake.
4. Synchronous intake commits CRM, receipt, minimal `lead.created` outbox event and dispatch job together. A response reports completed intake, while automation remains queued. Ambiguous contacts return a safe review conflict; producers must explicitly select an existing contact or attest an intentional distinct person, using the existing CRM review contract. No automatic merge.
5. A small worker claims one due PostgreSQL job using `SKIP LOCKED`, an expiring random lease token and generation. All internal effects and job completion occur in one fenced transaction. Bounded retries/backoff, attempt limits and safe terminal failures survive restarts. Poll at bounded intervals; process shutdown finishes bounded in-flight work.
6. One immutable schema-versioned workflow definition represents trigger, typed conditions and ordered internal activity steps. Editing creates a new immutable revision; publication validates it. Event dispatch binds an exact revision. Pausing cancels unstarted effects. No update event triggers, recursion, arbitrary expressions, SQL or code execution.
7. Tools declare version, input/output schemas, permission, side-effect/idempotency and deadline. The executor accepts only a claimed job reference/token and proposed supported arguments. PostgreSQL resolves tenant, integration, workflow revision, resource, correlation and publisher authority. Proposed identity fields are rejected. Audit and action are atomic.
8. Communication adapters remain mocks, deny sending by default, distinguish channels/purpose/suppression, and document durable intent plus reconciliation for future uncertain provider outcomes. No provider SDKs, accounts, credentials, model calls or network messaging.
9. Guided setup asks what triggers, optionally which leads, and what internal activity to record; review precedes activation. Drafts use existing scoped memory state. Show integrations, credential lifecycle, bounded run/receipt history, safe errors and recovery. Advanced editing is deferred; unsupported definitions open read-only and cannot be rewritten by the guided editor.
10. Verify incrementally: strict schemas and tool denial, real ordinary-role intake/replay/atomicity, cross-tenant boundaries, revocation ordering, competing workers, expired fencing, revision binding, API and UI flows. Final milestone includes existing security gates, reset and upgrade, lint/types/build, audit/secret scan and focused browser/accessibility/performance checks. Report unavailable checks explicitly.

## New privilege boundary and threat model

Dedicated NOLOGIN/NOSUPERUSER/NOBYPASSRLS function owners receive enumerated privileges only. Separate intake and worker LOGIN roles receive only named private entry functions and no table access or role memberships. Neither can read Auth, sessions, credentials or unrelated tenants directly. Human management wrappers remain SECURITY INVOKER with private implementations and empty search paths. Existing runtime role keeps its existing privileges.

Durable user delegation checks the publisher's current Owner/Admin membership and its membership generation under an organization SHARE lock; it does not reuse an expired session or manufacture a human JWT. Revocation/rejoining invalidates old authority. Integration intake similarly checks its authorizing administrator and credential expiry. Work is cancelled if integration or workflow is paused/revoked, or delegated authority is no longer valid. New publishers must explicitly reactivate after restoring authority. An operation admitted before revocation can finish; one behind a winning revocation is denied. This mirrors existing CRM ordering.

Only bounded private functions can establish execution scope. RLS independently constrains the execution owner to that scope; ordinary callers cannot assume that role. Composite FKs constrain every resource reference. Credentials are high-entropy random values, hashed with SHA-256, never ordinary read fields or log data. Quotas serialize per integration and bound intake/management/queue fanout. Body/schema/deadline limits and safe diagnostic codes constrain malicious payloads. Untrusted lead text never chooses actions, identity or policy.

## Tradeoffs and operational limits

PostgreSQL is the sole coordinator, avoiding a broker and distributed transactions. Synchronous bounded CRM acceptance simplifies payload retention and atomicity; a retry after response loss uses the original identity and canonical versioned fingerprint. Internal effects can be atomic with completion; arbitrary future provider calls cannot. Delivery is at least once, with controlled logical effects, never distributed exactly once.

Start with one trigger and an internal activity action. No status/assignment business rules are duplicated. A future visual editor must preserve the same definition, validate supported capabilities and round-trip without discarding fields. UTC scheduling is supported; business hours require explicit timezone/DST semantics later. Production needs separately reviewed provisioning of least-privilege logins, TLS, distributed gateway controls, retention/deletion, backups, monitoring, queue capacity and provider intent reconciliation. Local success is not production certification.

## Final implementation details

Private tenant ledgers use execution-scope RLS. Only the integration credential lookup and job claim tables have queue-wide policies for the NOLOGIN execution owner; their LOGIN callers have no table rights. The owner has no Auth/session reads or membership mutation rights. A policy-owned helper returns only a current administrator membership generation under the organization lock. Human management additionally uses the existing enrolled-session CRM context.

Intake stores immutable attempt IDs, external delivery identity, canonical fingerprints and safe codes independently from successful receipts. The first recorded attempt binds identity permanently; successful retries return the original IDs. CRM, event, receipt and successful attempt commit together. A nested failure transaction rolls back business effects and records only a rejected attempt. Existing deferred email/phone position constraints are forced inside the bounded intake function, then returned to deferred mode, so no table grant is needed on the intake LOGIN. Immutable creator constraints distinguish human and integration attribution.

The engine supports up to three typed AND conditions and three internal activity steps. The guided editor supports one activity and distinct source/status filters; larger or future capabilities are read-only. Publication appends a fresh immutable authority revision; edits leave the prior publication active. Events snapshot eligible published revisions at occurrence. Worker conditions inspect the current locked lead. Internal activities do not emit `lead.created`, preventing loops by construction.

Failed dispatch/run jobs can be retried by a current administrator with an expected fence generation. The request increments the fence, resets the bounded attempt budget and records a security audit event. Execution still checks the original publication authority and current integration/workflow status. Rejoining cannot revive a revoked generation. An exhausted crashed final lease becomes terminal rather than staying claimed forever. Job results and tool records contain safe identifiers/counts/codes, with intentional activity text stored only as CRM business content.

The guided builder offers activation directly after review, with Save draft as an option. If draft saving succeeds but activation is uncertain, it directs the user to reconcile the saved automation instead of creating another draft. Other uncertain management creates freeze until status review; management edits/lifecycle changes use optimistic versions. Integration keys remain transient in the creation view and are never copied into draft storage.

Official reference: [Supabase row-level security and explicit grants](https://supabase.com/docs/guides/database/postgres/row-level-security). The pinned local PostgreSQL behavior was verified with ordinary-role fixtures and the existing security suites. No hosted Supabase mutation was used.

System-owned dispatch reacts to a committed lead-created fact. Its originating human is audit provenance, not a reusable human session or grant. Effects run under the independently checked published workflow delegation; a revoked initiating member cannot use that fact to choose arbitrary tools or authority. Integration-originated events additionally require the currently authorized integration principal.
