# Phase 04 communication boundary

Baseline: clean local `main` at `2a329e6`, including merged Phase 03. No remote update, reset, provider account, or live delivery is required.

## Decisions before implementation

Keep the modular monolith and PostgreSQL coordinator. Communication jobs follow the existing fenced lease protocol, run in the existing development worker, and have a separate outbox relation because external submission has an uncertainty boundary unlike atomic internal automation actions. Existing automation definitions and execution remain unchanged. Future tools must call the same draft/authorize interfaces; outbound automation is intentionally unavailable.

Use a separate NOLOGIN/NOBYPASSRLS function owner, explicit grants, private RLS ledgers, composite tenant foreign keys, existing enrolled-session CRM context and current administrator generation bridge. Human reads/drafts require membership; send, evidence and operational controls require Owner/Admin. Worker and ingress logins receive only named functions, no tables or role membership. Organization locking orders revocation before dispatch admission. Pausing linearizes at the submission reservation: an already admitted operation may finish; no new operation is admitted afterward.

One conversation per organization/contact/optional lead/channel (NULLs compare equal). Messages snapshot destination and server-selected mock sender, retain one content copy, and have stable client draft IDs plus optimistic versions. Send approval binds the exact persisted version, approving administrator and membership generation. The immutable message event ledger is also the outbox audit; the delivery job is created atomically with approval. No message bodies or destinations are copied into audit/telemetry.

Explicit consent evidence is required for both transactional and marketing messages. Purpose, channel, destination, source, collection time, jurisdiction, disclosure/policy version and evidence reference are recorded. This conservative mock policy is not a jurisdictional legal determination. Unknown consent and unknown jurisdiction fail closed. Revocation/STOP/unsubscribe create destination suppression independently of consent. START never grants consent. Administrative removal of a suppression is explicit and does not manufacture consent. No CRM import/intake fabricates permission. Live delivery remains unsupported until jurisdiction-specific policy and provider onboarding have been separately reviewed.

States: `draft → queued → submitting → submitted → delivered | failed | bounced`; policy failure before admission becomes `suppressed`. Definitely unsubmitted retryable errors return to `queued` within a bounded attempt budget. Uncertain submission or expired submitting leases become `attention`; reconciliation queries provider state and never blindly resends. Terminal events cannot regress delivered/bounced/failed state; opt-outs still suppress the destination even when delivery is already final. Duplicate normalized provider event identities have no second effect. Unknown events are acknowledged without choosing a tenant from the payload.

Mock email/SMS are pure deterministic adapters with explicit 5-second deadlines and stable message-derived identities. Mock acceptance and mocked delivery are distinct worker passes. No provider SDK or network sending implementation is installed. Configuration rejects live modes/enablement, including in development. Signed mock webhooks use isolated HMAC-SHA256, timestamp freshness and exact raw bytes, with bounded payloads; these are not Resend/Twilio webhooks. Production mock webhooks are disabled.

PostgreSQL reservations serialize organization/day, destination/day, channel/day, in-flight submissions and provider/minute budgets. Retries consume request budgets. Fixed UTC windows and bounded defaults are visible in settings; all authoritative counters live in PostgreSQL. Scheduling/quiet hours are unavailable, so there is no unsafe timezone inference. Mock sender identities are fixed server-side and cannot be substituted by clients.

## Privacy and threat model

Private tables have no browser grants. Bounded reads apply authorization before scope, keyset pagination and tenant indexes. Events contain safe lifecycle codes and IDs only. Signing keys stay server-only; bodies/signatures are never ordinary logs. Raw webhook payloads are discarded after normalization. Current retention is indefinite business history and permanent idempotency tombstones; there is no application delete/purge endpoint. Before real use, define approved retention, legal holds, encrypted backups, content redaction/deletion while preserving identities, incident response and provider event retention. Do not represent this local foundation as production certification.

Threats addressed: cross-tenant IDs/sender injection, direct RPC bypass, revoked approval, opt-out after enqueue, concurrent duplicate sends, forged/replayed webhook, stale lease completion, restart after submission, unbounded retry/queue growth and misleading success UI. Privileged migration administration, compromised server/worker/signing key, production gateway abuse, legal policy coverage and external exactly-once delivery remain operational boundaries.

## Implemented API and operating contract

Human routes are under `/v1/organizations/:org/communications`. GET settings/conversations/conversation history/message/events/contact eligibility use strict shared response contracts and membership authorization. PUT message creates/edits a draft by stable UUID and optional current version. POST send binds the exact saved version; POST reconcile never requeues a send. POST permission/suppression and PUT settings require current Owner/Admin. Browser cookies, enrolled-session checks and CSRF are inherited unchanged. List/history/event pages are limited to 50/50/100 respectively with timestamp+UUID keysets; joins carry organization IDs. The history response also carries a bounded 500-event summary, while the dedicated per-message event endpoint provides complete paginated access. A message destination must still belong to its current active contact at dispatch.

`AutomationDatabase` exposes named communication claim/prepare/finish methods only to its worker mode and normalized event ingestion only to ingress mode. The existing worker processes at most one communication and one automation job per iteration, preserving fairness with bounded pools, deadlines and graceful shutdown. Communication jobs are a private PostgreSQL outbox relation, not a new queue service. A claim alone cannot finish a queued message: preparation must persist the provider reference and submission state first. Completion verifies the current token, generation, expiry, reference and state. Expired submission is reconciled, never automatically resent. Only a typed definitely-unsubmitted error is retryable; generic errors/deadlines become attention. Backoff is bounded exponential plus jitter, maximum five configurable attempts. The mock reconciler deterministically derives outcomes; it does not prove external submission or delivery.

Authoritative limits reserve under the organization communication lock. Daily dimensions are organization, channel and hashed destination, with distinct per-minute request counters, in-flight submission counts, and a globally locked mock-provider counter. Uncertain in-flight work continues to consume its reservation. Throttled work is durably deferred; daily exhaustion suppresses the message with an inspectable reason. Webhook admission also has a 120 fresh-event/organization/minute PostgreSQL cap, after duplicate-event detection. The transport rate limiter is an additional process-local guard, not the authoritative distributed quota.

The signed mock event resolves its tenant from an indexed durable job/message reference. It cannot supply a tenant, sender or actor. Terminal states do not regress; even late opt-outs/bounces retain suppression. Duplicate event identities are stored once. Malformed/unmapped references do not disclose ownership. The full provider request body/signature is never retained. Exact-byte verification happens before JSON parsing and normalization, at a 16 KiB body limit. Webhooks are disabled in production and unavailable without configuration.

### Environment and credentials

| Setting                                              | Behavior                                                                                                                                                                        |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `COMMUNICATIONS_MODE`                                | Absent or `mock` only; every other value fails startup.                                                                                                                         |
| `OUTBOUND_LIVE_ENABLED`                              | Absent or `false` only; `true` fails startup in every environment.                                                                                                              |
| `MOCK_WEBHOOK_SECRET`                                | Optional canonical base64 encoding of 32 random bytes, server-only; distinct from session keys. Without it, mock webhooks are unavailable. Never use it as a Resend/Twilio key. |
| `WORKER_DATABASE_URL`                                | Existing restricted `leadsfam_worker` login; communication entry functions added, no table access.                                                                              |
| `INGRESS_DATABASE_URL`                               | Existing restricted `leadsfam_ingress` login; signed mock-event entry function added.                                                                                           |
| `SESSION_DATABASE_URL`, session keys, CRM cursor key | Existing contracts preserved; no new frontend credential.                                                                                                                       |

The local launcher stores generated signing material in the existing mode-0600 OS-temporary secret file, never Git. Restart the launcher to inject the new setting into older running processes. There is no persistent tenant credential store or real provider adapter in this phase. Installing credentials or setting a flag cannot accidentally turn the mocks into live delivery.

### Remaining operational boundaries

The mock policy requires explicit evidence for both service and marketing, and fails unsupported jurisdictions closed. It is a synthetic safety policy, not a complete legal rules engine. Jurisdiction-specific law, quiet hours/DST, verified sender onboarding, encrypted tenant credentials, official vendor webhook mechanisms, provider-managed opt-out scope, reconciliation guarantees, retention/deletion, live-provider capacity and production operational readiness require review before adding a live adapter. The Supabase changelog identified recent timezone-data changes; scheduling is explicitly unavailable rather than inferring recipient timezones.

RLS and explicit function grants follow the [Supabase security guidance](https://supabase.com/docs/guides/database/postgres/row-level-security). The new role receives no Auth/session table access, role inheritance, membership mutation or BYPASSRLS. Existing Phase 02F and Phase 03 policies/functions are preserved; only additional named policies for the communication owner read CRM records. See the [manual walkthrough](../phases/phase-04-manual.md) and [verification report](../phases/phase-04-report.md).
