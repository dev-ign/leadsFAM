# Phase 02 CRM architecture and contracts

LeadsFam remains one React app and one Fastify API. CRM, intake, history and attribution are modules, not services. The server-only database package owns generated SQL types, the restricted session-pool factory and typed user-JWT RPC transport. Shared owns Zod/wire contracts and presentation permissions. UI owns reusable primitives. Web owns screens and ephemeral state; it has no database dependency. Deferred agents, workers, integrations and observability packages remain absent.

## Records and relationships

A contact is a person or company within an organization; a lead is one inquiry belonging to that contact. A returning contact gets another lead. Missing email/phone is valid. Position one is primary and there are at most three of each channel. A company requires a company name. UUIDs are identifiers, never permission.

All eleven relations have RLS; the administrator owns them. Public authenticated roles have SELECT subject to enrolled-session/current-member RLS, and no direct CRM DML. Private ledgers have no browser table grants. The dedicated CRM NOLOGIN/NOBYPASSRLS role owns bounded functions and explicit DML rights, with independent scope-plus-current-membership policies. It inherits no roles and cannot access Auth or the application session store. [ADR 0010](../decisions/0010-crm-privilege-review.md) records the pre-migration review and negative tests. Generated search columns are excluded from DTOs and cannot be set by clients.

## Identity, authority and isolation

Authentication verifies the person through the existing encrypted server-managed session and Supabase Auth. Authorization checks the person's current role for this operation in this organization. Isolation limits rows and relationships independently using RLS, explicit grants and composite FKs. For example, `(org,contact_id)` must reference that organization's contact even if the supplied UUID names a real foreign contact.

A URL organization is a request, not trusted context. The API resolves it using a verified application session and current database membership. The operation RPC checks again under the organization SHARE lock. Membership changes take an exclusive lock and recheck after waiting. An admitted operation may finish before revocation; queued/later operations are denied once revocation wins. Recovery or unenrolled JWTs never gain CRM access. No new Auth/session privilege was added.

| Capability                                                                                         | Owner         | Admin         | Member                                                     |
| -------------------------------------------------------------------------------------------------- | ------------- | ------------- | ---------------------------------------------------------- |
| Read contacts/leads/history/sources; create/edit contacts and open leads; normal transitions/close | Yes           | Yes           | Yes                                                        |
| Assign/reassign to an eligible current member                                                      | Yes           | Yes           | Self claim/release only; cannot take another person's lead |
| Reopen closed lead with reason                                                                     | Yes           | Yes           | No                                                         |
| Archive/restore contact or lead; administer sources                                                | Yes           | Yes           | No                                                         |
| Preview/execute/read import jobs                                                                   | Yes           | Yes           | No                                                         |
| Hard delete, merge, export, outbound integrations or AI execution                                  | Unimplemented | Unimplemented | Unimplemented                                              |

Shared `can` labels centralize API/UI presentation checks and mirror the existing matrix; they grant no database authority. PostgreSQL independently enforces the matrix for direct RPC. No Phase 01 policy or session behavior changed.

## Lifecycle, history and concurrency

`new` means a fresh inquiry. It can enter `in_progress`, `qualified` or `closed`. `in_progress` means active follow-up; it can qualify or close. `qualified` means a human has found a suitable opportunity; it can return to in-progress or close. `closed` requires won/lost/unqualified and a close timestamp. Only Owner/Admin may reopen, with a reason, into in-progress; current close fields clear while immutable transition events retain the prior outcome. Ordinary edits and assignment require an open lead. Archive is separate from lifecycle; a contact cannot be archived while it has open, unarchived leads, and a lead cannot be restored under an archived contact.

Every mutable aggregate has a version. A stale submitted version returns `409 VERSION_CONFLICT`, with no lost update or extra activity. Organization/contact/lead locks and ordered import claims prevent conflicting writes; expected domain row failures use subtransactions. Assignment retains member ID and membership generation. Revocation/rejoining changes that generation; old assignment remains history but cannot become current again by rejoining.

Current lead/contact views resolve current contact information. Editing a shared contact updates every lead view, but never rewrites acquisition or activity history. A contact's first touch is the earliest accepted lead, including archived leads. Detail screens show the latest 25 related leads; the complete paginated list is available through the contact filter API. Keyset pagination uses timestamp plus UUID, not an offset or a frozen snapshot.

## Intake and import

[ADR 0011](../decisions/0011-crm-domain-and-retries.md) defines identity, matching and replay. Email normalization trims/lowercases while preserving dots and plus tags; phone normalization uses validated E.164 only with sufficient international/region context. Exact normalized channels or normalized names suggest candidates, capped at ten. A suggestion is not proof of identity: reuse requires an explicit selection, or choose a distinct contact. No automatic merge/link occurs, including for matching rows in one import.

Manual contact/lead creation requires a UUID `Idempotency-Key`. A separate inquiry uses a new key even for the same contact. Identical retry returns the original IDs; incompatible canonical content with the same key conflicts. A replay resolves current authorized contact data, rather than promising byte-identical historical PII.

CSV uses distinct job, immutable attempt and persistent logical delivery UUIDs. Correcting a failed row needs a new attempt, retaining delivery ID and row order. Identical attempt replay returns its historical result; first successful delivery IDs never change. Changed content for a successful delivery fails safely. Expected row errors permit partial success. Unexpected infrastructure errors roll back the entire attempt, including business writes. The same transactional contract passed the independent specification, PostgreSQL and real HTTP suites, including an actual API restart after commit with response loss.

CSV is synchronous and strictly bounded: UTF-8 with optional BOM, comma-delimited, 256 KiB raw text, 100 data rows, 16 explicitly mapped columns, 4 KiB fields/16 KiB records. API JSON envelopes have a 512 KiB limit only on import endpoints; other routes retain 16 KiB. Malformed encoding, duplicate/unexpected headers, conflicting mapping and invalid rows fail safely. Preview is read-only. No formula evaluation, file forwarding, raw-row error persistence or CSV export exists. A future export must neutralize spreadsheet formulas. Larger imports require a separately reviewed durable worker/outbox design.

## HTTP contracts

All tenant endpoints below are under `/v1/organizations/:org`. GET reads need a verified application cookie. Every mutation additionally requires an allowed Origin and session-bound CSRF header. Actors/timestamps/tenant scope are derived server-side. Exact input/output contracts live in [shared CRM schemas](../../packages/shared/src/crm.ts); web uses the centralized typed [API client](../../apps/web/src/lib/api-client.ts).

| Route                                                                                     | Purpose                                                                                                                                                           |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /contacts`, `GET /leads`                                                             | Bounded `q`, searchMode prefix/contains, dates/archive, pageSize ≤100/default25; lead status/priority/source/assignee/contact/sort filters; items + opaque cursor |
| `GET /contacts/:id`, `GET /leads/:id`                                                     | Explicit current DTO, foreign IDs indistinguishable from absent                                                                                                   |
| `POST /contacts/candidates`                                                               | Normalized explicit duplicate review, ≤10 candidates                                                                                                              |
| `POST /contacts`, `PATCH /contacts/:id`                                                   | Idempotent create or versioned edit                                                                                                                               |
| `POST /leads`, `PATCH /leads/:id`                                                         | Transactional contact resolution + lead/attribution/activity/receipt; versioned ordinary edit                                                                     |
| `POST /leads/:id/transitions`, `PUT /leads/:id/assignee`                                  | Versioned lifecycle/outcome/reason and assignment                                                                                                                 |
| `POST /{contacts,leads}/:id/{archive,restore}`                                            | Versioned reversible archive                                                                                                                                      |
| `GET /{contacts,leads}/:id/activity`                                                      | Bounded cursor timeline; shared-contact events included                                                                                                           |
| `GET/POST /lead-sources`, `PATCH /lead-sources/:id`                                       | Catalog read/admin                                                                                                                                                |
| `POST /lead-imports/columns`, `/lead-imports/preview`                                     | Bounded parse/mapping and stateless preview                                                                                                                       |
| `POST /lead-imports`                                                                      | Job/attempt/delivery submission with durable row results                                                                                                          |
| `GET /lead-imports`, `GET /lead-imports/:job`, `GET /lead-imports/:job/attempts/:attempt` | Latest25 jobs, complete job manifest/latest10 attempts, or exact attempt                                                                                          |

Errors use safe `{error:{code,message,requestId}}`: 401 no application authentication; 403 forbidden/CSRF; 404 unavailable resource; 409 version/idempotency/review/lifecycle conflict; 413 size limit; 422 invalid import/fields; 503 dependency failure or bounded timeout. Strict schemas reject unknown fields. Raw PostgreSQL details, request bodies, contact data, search terms and cursor bodies are excluded from application logs.

`/health` is public liveness. `/ready` probes restricted SQL, Auth and PostgREST and returns only ready/unavailable. Its response deadline does not cancel an already queued SQL probe; existing pool deadlines bound that work. Readiness does not certify RLS, migrations, backups or production readiness.

## Frontend and operational limits

The data router supports unsaved-navigation blocking. New CRM drafts live in memory, keyed by verified user/org/form, above the revalidation gate. Same-identity verification restores them with their original edit version; sign-out/user/role/revocation/org changes clear or isolate them. No sensitive draft goes into browser storage, URL or cross-tab messages. Late query/save callbacks cannot populate another scope. Uncertain creates/imports freeze their submitted payload/key for identical retry. A hard refresh loses in-memory manual drafts; browser warnings are best effort. Imports can recover durable results via their job URL. Old Phase 01 note/settings forms were not converted into a persistent draft system.

The dedicated cursor HMAC key must be separate from session encryption keys. Cursors bind user/org/entity/query/search mode/order/page size and exact timestamp/UUID, expire after 30 minutes, and contain no raw search terms. Key rotation invalidates pagination only. Production requires this key explicitly; local bootstrap creates mode-0600 development keys outside Git and shares macOS TMPDIR consistently through Turbo.

Retention has no automatic purge in Phase 02. Application administrators cannot hard-delete history through CRM, but database operators remain trusted and can read/alter data. Before real data, decide retention, privacy deletion/export, backup restore and consent separately; possessing an email is not marketing consent. No compliance certification is claimed.
