# Phase 04 engineering report

Local implementation on `codex/phase-04-communications`, based on clean, updated local `main` at `2a329e6`. No pull, commit, push, merge, deployment, database reset, real-provider account or external customer delivery was performed. Risk level 4, including level 3 tenant authorization, consent, RLS and durable messaging.

## 1. Executive summary

Authorized members can prepare persistent email/SMS drafts, reopen them from conversation history, and inspect the same history from contacts and leads. Current Owners/Admins can record evidence, manage suppression, set sending limits, pause submissions and approve the exact saved draft version. PostgreSQL atomically persists approval and its delivery outbox record. The existing development worker dispatches through deterministic mock adapters, records acceptance separately from simulated delivery, reconciles statuses and preserves inspectable lifecycle events.

Cross-tenant IDs, unauthorized sends, stale leases, duplicated approval/webhook requests, missing consent, changed recipients, opt-out before dispatch and revoked authority are covered. Provider deadlines become attention rather than automatic resend. No environment setting can enable a live provider in this implementation. A mock delivered status is not a successfully delivered customer message.

## 2. Architecture decisions

- Preserve the modular monolith and PostgreSQL coordinator. The separate communication outbox follows Phase 03's lease/fencing pattern because external submission has an uncertainty boundary that internal transactional activity execution does not. The existing worker services both domains; no broker, service, SDK or dependency was added.
- Private, tenant-scoped ledgers and a dedicated NOLOGIN/NOBYPASSRLS owner preserve the existing least-privilege model. Existing worker/ingress logins receive only named additional capabilities. Human RPCs reuse enrolled sessions, CSRF, organization locks and current administrator membership generations.
- One conversation per organization/contact/optional lead/channel, with NULL-safe uniqueness. Stable draft UUIDs identify intentional messages; optimistic versions bind editing and human approval. Destination, sender and content become immutable after approval.
- Explicit evidence is required for each channel/purpose/destination, including service messages. Independent destination suppression wins over consent. Unknown/unsupported jurisdiction fails closed in the conservative mock policy. This is not a complete legal rules engine; live delivery remains unavailable.
- Provider adapters receive only database-prepared envelopes. Server-selected simulation senders and fixed mock identity prevent client-selected credentials/senders. Unknown outcomes require reconciliation, not blind retry. Future AI tools must use these secured draft/approval capabilities; no outbound workflow action was enabled.

The full state machine, privilege boundary, environment contract, retention behavior and threat model are in [the architecture document](../architecture/phase-04.md).

## 4. Security report

Current organization membership is checked on reads/drafts; approval/evidence/settings/suppression require Owner/Admin. Dispatch rechecks the approving administrator and its membership generation under the existing organization lock, contact/destination ownership, consent and suppression. Rejoining cannot revive an old approval. Organization/channel/destination budgets, concurrent submissions and provider request reservations are PostgreSQL-enforced. Pause stops new admission; already admitted submissions may complete, and provider-accepted work still reconciles.

Private communication tables have no browser/runtime/worker/ingress table grants. The new owner has no Auth/session table access, role inheritance, membership mutation, CREATE privilege after provisioning or BYPASSRLS. Composite tenant foreign keys, empty function search paths, closed function ACLs and strict RPC inputs preserve isolation. Existing Phase 02F/03 policies are unchanged; new CRM read policies apply only to the communication owner. Final local advisors report no findings.

Mock webhooks authenticate exact raw bytes before JSON parsing, enforce a 16 KiB bound and five-minute timestamp freshness, deduplicate durable identities and resolve tenant/provider ownership from the persisted job reference. A PostgreSQL webhook cap supplements the transport limiter. STOP/unsubscribe and bounce suppress the destination even after final delivery; START never grants permission or clears suppression. No unsigned or production mock-webhook bypass exists.

Ordinary telemetry excludes bodies, personal destinations, credentials, signatures and raw webhook payloads. Message content has one business-record copy; events/audits store safe codes and identifiers. History/evidence/idempotency identities currently have indefinite retention and no application purge endpoint. Approved retention/deletion/export/legal-hold behavior must precede live use.

Remaining operational boundaries: privileged database/server administrators, signing-key compromise, production gateway abuse, full jurisdictional compliance, tenant-owned live credentials and sender onboarding, real-provider event formats/reconciliation, retention administration, monitoring/capacity and independent security review. Local passing tests do not certify production readiness.

Dependency audit: **zero high/critical**, one pre-existing moderate development-only `minimatch` 10.2.6 advisory, [GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249), for glob-pattern resource amplification. The advisory lists a fix in 11.0.1+. Dependency manifests/lockfile versions were not changed by Phase 04. Review a compatible tooling update separately rather than silently forcing a transitive major upgrade. Working-tree/history secret scanning and credential canaries passed.

## 8. Known limitations

- Email and SMS delivery are deterministic simulations. No Resend/Twilio adapter, account, encrypted tenant credential store, verified live sender or real-provider webhook is implemented. Unsupported live configuration fails startup.
- The mock policy accepts only explicit evidenced permission and a bounded example jurisdiction set. It is not legal authorization for outreach. Production policy/legal review remains necessary.
- No autonomous/AI sending, outbound workflow action, bulk campaign, scheduling, SMS quiet hours or general inbound-content inbox. The schema anticipates direction, but this phase ingests normalized delivery/opt-out events rather than general inbound message bodies.
- Unknown provider outcomes remain attention until a verified event or explicit status reconciliation resolves them. Processing attempts include send and lookup work; reducing the budget to one can require manual reconciliation after acceptance. No exactly-once external guarantee is claimed.
- History/evidence/identity retention is indefinite until a separately reviewed purge/redaction design. Budget-window retention/compaction and many-large-tenant capacity remain operational work.
- The moderate development-tool advisory, frontend bundle advisory and production-readiness work above remain visible and unresolved.

## 9. Next-phase recommendations

Future AI agents can propose bounded message drafts through the same typed capabilities, with organization and actor bound by trusted backend context. Preserve human approval of exact content/purpose/destination, current membership-generation checks, consent/suppression and budget enforcement outside model reasoning. Do not give models provider credentials, direct send access or effective tenant/actor arguments.

Before any live adapter, implement and review tenant credential/sender ownership, provider-specific idempotency and official signature verification, authenticated opt-out scope, legal/jurisdiction policy, quiet hours/timezone data, outcome reconciliation, content retention/deletion, monitoring and an explicitly authorized test-provider rollout. Address the tooling advisory and bundle size in a focused maintenance change. A later UX refinement can reuse these contracts and state machine without redesigning the security boundary.
