## A. Phase 06 closure

### Finding C1 — bound results before persistence (P2, required before closure)

The worker validates the outcome's fields and character lengths, then calls `finishAi` outside its validation exception boundary. The existing database constraint limits `private.ai_runs.result` to **16,000 bytes of JSONB text**, while the provider response ceiling is **32,000 bytes**. The expanded qualification evidence can fit the provider/schema limits and exceed the database limit.

A memory-only synthetic reproduction, using the current built worker and grounding validator, produced:

| Observation                                       | Actual result                                                    |
| ------------------------------------------------- | ---------------------------------------------------------------- |
| Source JSON                                       | 2,409 UTF-8 bytes                                                |
| Simulated provider response                       | 21,731 UTF-8 bytes, below 32,000                                 |
| Grounding/schema validation                       | Accepted                                                         |
| Serialized final result                           | 21,587 UTF-8 bytes, already above 16,000 before JSONB formatting |
| Simulated database-size enforcement at completion | Rejected                                                         |

No actual model or database call was made by this reproduction. It used eight required answers and eight requirement excerpts with repeated multibyte evidence. The actual SQL constraint confirms why the same oversized result cannot persist. The finish transaction would roll back its attempt/usage and run updates, leaving a claimed job until lease recovery. Real-mode lease recovery eventually requires attention and prevents a blind paid retry, but it does not preserve the supplied usage or produce an immediate size-validation failure.

Correction proposal, **not implemented here**: bring the final serialized-result budget into alignment with the JSONB storage limit inside the existing failure boundary; finish rejected results with a safe code and null result while preserving supplied usage and fencing. Account for JSONB serialization overhead. Keep the existing database limit unless a separately justified requirement needs a change. Extend the existing provider/worker and AI database tests with multibyte boundary cases. No new queue, table or provider is needed.

Evidence: [worker completion](../../../../apps/api/src/modules/ai/execute.ts), [original result-size constraint](../../../../supabase/migrations/20261101205116_ai_foundation.sql), [Phase 06 completion function](../../../../supabase/migrations/20261103025508_ai_intelligence.sql).

## D. Minimum viable candidate implementation

### Required functionality, in priority order

1. **Verified, tenant-bound mock ingress for email and SMS.** Keep it disabled in production, consistent with the current mock webhook. Verify bounded raw bytes and timestamp/signature before parsing. Resolve the workspace from a server-owned connector binding with an explicit inbound purpose; ignore caller-provided organization authority. Reuse integration credential lifecycle/admin UX and verifier patterns without granting existing lead-intake credentials new capabilities. Check current activation, expiry, revocation and authorizer authority at the database boundary.
2. **Atomic durable receipts and replay/conflict handling.** Scope event identity by organization and connector, retain a bounded normalized fingerprint, and atomically create the receipt, conversation/message and audit result. Same event and payload returns the same logical result; changed payload under the same event identity conflicts. Acknowledgment follows commit. If bounded synchronous processing suffices, use an existing PostgreSQL transaction and caller retry rather than adding another job system. If work genuinely needs asynchronous processing, use the existing claim/fence protocol.
3. **Conservative contact, lead and conversation attribution.** Prefer an authenticated reply reference to an existing message, validated in the connector's workspace. Otherwise match only an unambiguous normalized saved contact address in that workspace; an email address or phone number alone must not select among several leads. Unknown or ambiguous references go to a durable review state with a clear reason. A member can explicitly link them to an authorized contact/lead through a bounded review action; never guess, merge contacts or create a new lead by default. Validate the lead belongs to that contact and organization, not merely two independent tenant FKs.
4. **Truthful provenance and readable conversations.** Record the connector as creator of an inbound message rather than impersonating its owner/authorizer. Display incoming text in the existing conversation screen, with channel, time, safe status and synthetic provenance. Reuse pagination and add a small needs-review view/action for unmatched receipts. Out-of-order timestamps must have a stable, documented ordering; provider timestamps never replace server audit time.
5. **Preserve all existing control boundaries.** Inbound content is untrusted data. It cannot edit CRM truth, infer consent, clear suppression, select a different tenant/recipient, publish workflows, approve a draft or queue a send. Outbound mutations and workers explicitly reject inbound messages. Any AI use is a separate existing human action; exact-version approval and mock-only sending remain unchanged.

Items 1–5 are essential to the recovered mock-inbound objective. Automatic analysis/follow-up, escalation/cancellation workflows and broad conversation orchestration are deferred: the same original November 4 proposal places those in a subsequent phase. This separation is source-based, not a newly invented roadmap.

### Security and tenant isolation

Use organization-scoped composite references and RLS on every new relation, plus explicit contact/lead/conversation consistency checks. Resolve tenant authority before business matching; identical addresses in different workspaces are unrelated. Fail closed on foreign reply IDs, revoked/expired connectors, ambiguous matches, invalid signatures and stale timestamps. Recheck connector authority in the committing transaction, including concurrent revocation. Bound body bytes, identifiers, retained unmatched payloads, request rates and history pages. Store only normalized content needed for the workflow; do not retain raw headers, keys or full provider payloads by default. Sanitize rendered text, errors and logs. Real customer data and real provider ingress remain subject to privacy/retention acceptance.

A signature proves the configured mock transport's authenticity, not the identity or honesty of a customer. Mock signature verification is also not validation of a future provider's different signature/replay rules. Incoming text can supply attributed customer statements to existing analysis, but cannot grant model authority. Its receipt must never create a communication job or alter consent/approval state.
