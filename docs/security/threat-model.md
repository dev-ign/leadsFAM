# Phase 01 threat model

Scope: the local React SPA, Fastify API, Supabase Auth/PostgreSQL/PostgREST/Mailpit stack and engineering gates. No hosted production system, real customer data, worker or agent execution exists. This is tested local implementation, not a production security certification.

| Threat                                             | Implemented control                                                                                                                                                                                            | Remaining limitation / launch requirement                                                                                                                                                |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged identity / account takeover                 | Auth `/user` verifies server-held bearer credentials; email verification, opaque cookie rotation, idle/absolute expiry, revocation and recovery-specific purpose                                               | MFA/sensitive-action reauthentication, account-abuse policy, CAPTCHA or equivalent, production identity operations                                                                       |
| Recovery token grants organization access          | Database requires active application enrollment matching user/provider session; real recovery JWT tested through API and raw Data API; completion fence revokes sessions and rejects overlapping sign-ins      | Recovery and provider password update span systems; a failure leaves enrollment blocked until recovery succeeds; support runbook required                                                |
| Cross-tenant data leak / resource guessing         | Backend-derived organization context, current membership checks in locked RPCs, RLS, explicit grants, immutable tenant identity and composite FKs                                                              | Already returned data cannot be recalled; direct SELECT uses statement snapshots; keep regression tests for every new table and operation                                                |
| Role escalation / owner removal / invitation races | No direct lifecycle writes; owner/admin/member matrix; ownerless-org constraint; matching verified email, single-use/expiry checks and current inviter authority                                               | Owner transfer/deletion intentionally unavailable; reviewed recovery/administration process required before exposing them                                                                |
| Privileged database bypass                         | Ordinary tenant requests use user JWT; runtime session role has no tenant/Auth grants; bounded private functions, fixed search paths and NOLOGIN/NOBYPASSRLS owner                                             | Function-owner policies are powerful and require review. The explicitly approved no-argument verified-email helper executes as `postgres`; database administrators remain trusted        |
| Token/key leakage                                  | Provider tokens encrypted with versioned AES-GCM and row identity binding; cookie contains random ID; no browser token storage; logs omit bodies/headers/query values; checksum-verified Gitleaks and canaries | Runtime memory/key compromise exposes sessions; secret manager, two-stage key rotation, backups and incident revocation needed. Local keys live outside Git in mode-0600 temporary files |
| CSRF and cookie abuse                              | Allowed Origin plus session-bound CSRF on every mutation, SameSite=Lax/HttpOnly/host-only cookies; production `__Host-` + Secure; exact credentialed CORS only for `/v1/`                                      | Requires same-site deployment topology, HTTPS and reviewed proxy configuration. Cookie path/domain are not authorization boundaries                                                      |
| XSS / malicious presentation input                 | React text rendering, bounded input schemas, no raw HTML; API Helmet; no provider tokens accessible to frontend JavaScript                                                                                     | HttpOnly does not stop an XSS script from issuing authenticated actions; frontend CSP/security headers and dependency controls required at deployment                                    |
| Session race, refresh loss, infrastructure failure | Session row locks, five-second provider timeouts, database statement/connect timeouts, fail-closed validation, per-user reset fence, bounded cleanup with safe failure logs                                    | Remote refresh then failed persistence may require sign-in again; bounded requests cannot make cross-system operations atomic; production fault/load testing remains                     |
| Resource exhaustion / credential attacks           | 16 KiB bodies, default 120 requests/IP/minute, sensitive auth 20/route/IP/minute, organization creation 5/IP/hour, invitations 20/IP/hour, no proxy trust                                                      | In-memory rate limits are per process, reset at restart and do not protect raw Auth/PostgREST access. Distributed/gateway limits, quotas, direct signup abuse and monitoring need review |
| Audit repudiation                                  | Private append-only security events with verified actor, event, organization where applicable, generated API request ID; structured request logs                                                               | Direct Data API request correlation can be client-supplied; no external audit sink, retention, alerting, tamper-evident export or backup policy. Administrators can edit local records   |
| Supply chain and accidental secrets                | Pinned versions/lockfile/engines, strict peers, package boundaries, pinned CI actions, blocking types/lint/tests/build, full audit and working-tree/history secret scans                                       | High/critical audit blocks; low/moderate findings need documented triage. Scanning cannot prove all secrets absent or dependencies harmless                                              |
| Prompt injection / unauthorized outbound action    | Agents, tools, scraping, customer ingestion, SMS/email production providers, billing and workers are unimplemented                                                                                             | Design permission, consent, idempotency, budgets, job scopes and human approvals before any such capability                                                                              |

Authentication, authorization and data isolation have separate tests. Ordinary-role SQL tests establish policy behavior; real Auth tests establish credential verification and recovery behavior. Neither substitutes for the other. `user_metadata` is presentation-only. Current verified email is read through the approved caller-bound helper; stale JWT email cannot determine invitation authority.

Membership mutations lock the organization exclusively. Reads with an explicit ordering guarantee use a shared lock. Both recheck current membership after acquiring the lock. An authorized request may complete before revocation; a request waiting behind revocation is denied. The session registry is checked by the database on the later operation as well as by the API. No global mutable “current organization” is trusted.

Production organization creation is blocked in API configuration and defaults off in a private migration setting. Auth signup is enabled only for the local flow and must receive an independent production abuse/onboarding decision; blocking organization creation alone does not prevent identity signup abuse. The local seed must never run in staging/production.

The working-tree secret scan includes ignored environment files. Generated dependencies/builds/tools/Git object files are excluded; Git history is scanned separately. Provider-key, session-encryption-key and database-URL canaries must be detected before the real scan proceeds. No silent rule suppression or peer-dependency bypass is accepted.

Architecture, security, learning guides and migrations are eligible for version control; the blanket `/docs/` exclusion was removed. Nothing was staged, committed or pushed as part of this implementation.

Local container network inspection is a separate gate. The CLI's default host publication initially used wildcard IPv4/IPv6 interfaces, and a project bridge loopback option alone was ignored by Docker Desktop. Work stopped for review. The user approved the Desktop-wide “Localhost by default” setting; it was applied with no unrelated containers running. Docker publication and macOS listeners then both showed only `127.0.0.1` / `::1` for database, gateway, Studio and Mailpit. The clean reset and full database security gate passed afterward. The project retains a post-start actual-address assertion, local-bootstrap check and CI binding gate. Configure the Desktop default before first startup; the post-start check detects regressions rather than preventing the CLI from briefly creating a listener. Studio, Mailpit and database credentials are development conveniences and must never be publicly exposed.
