# Phase 01 threat model

Scope: the local React SPA, Fastify API, Supabase Auth/PostgreSQL/PostgREST/Mailpit stack and engineering gates. No hosted production system, real customer data, worker or agent execution exists. This is tested local implementation, not a production security certification.

| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Forged identity / account takeover                 | Auth `/user` verifies server-held bearer credentials; email verification, opaque cookie rotation, idle/absolute expiry, revocation and recovery-specific purpose                                               | MFA/sensitive-action reauthentication, account-abuse policy, CAPTCHA or equivalent, production identity operations                                                                       |

Authentication, authorization and data isolation have separate tests. Ordinary-role SQL tests establish policy behavior; real Auth tests establish credential verification and recovery behavior. Neither substitutes for the other. `user_metadata` is presentation-only. Current verified email is read through the approved caller-bound helper; stale JWT email cannot determine invitation authority.

Membership mutations lock the organization exclusively. Reads with an explicit ordering guarantee use a shared lock. Both recheck current membership after acquiring the lock. An authorized request may complete before revocation; a request waiting behind revocation is denied. The session registry is checked by the database on the later operation as well as by the API. No global mutable “current organization” is trusted.

Production organization creation is blocked in API configuration and defaults off in a private migration setting. Auth signup is enabled only for the local flow and must receive an independent production abuse/onboarding decision; blocking organization creation alone does not prevent identity signup abuse. The local seed must never run in staging/production.

The working-tree secret scan includes ignored environment files. Generated dependencies/builds/tools/Git object files are excluded; Git history is scanned separately. Provider-key, session-encryption-key and database-URL canaries must be detected before the real scan proceeds. No silent rule suppression or peer-dependency bypass is accepted.

Architecture, security, learning guides and migrations are eligible for version control; the blanket `/docs/` exclusion was removed. Nothing was staged, committed or pushed as part of this implementation.

Local container network inspection is a separate gate. The CLI's default host publication initially used wildcard IPv4/IPv6 interfaces, and a project bridge loopback option alone was ignored by Docker Desktop. Work stopped for review. The user approved the Desktop-wide “Localhost by default” setting; it was applied with no unrelated containers running. Docker publication and macOS listeners then both showed only `127.0.0.1` / `::1` for database, gateway, Studio and Mailpit. The clean reset and full database security gate passed afterward. The project retains a post-start actual-address assertion, local-bootstrap check and CI binding gate. Configure the Desktop default before first startup; the post-start check detects regressions rather than preventing the CLI from briefly creating a listener. Studio, Mailpit and database credentials are development conveniences and must never be publicly exposed.

## Phase 02 CRM extension

The reviewed CRM role has no login, inherited role, BYPASSRLS, Auth usage or session-store access. All eleven CRM relations have RLS and administrator ownership. Direct public DML is denied. Composite tenant FKs, immutable identities/history, version checks and backend-derived actors cover resource guessing, cross-tenant references, mass assignment and activity forgery. New CRM policies retain volatile current membership/session checks; performance work changes query shapes/indexes, not policy evaluation or privileges. See [the privilege review](../decisions/0010-crm-privilege-review.md).

CSV inputs are untrusted and bounded before execution; preview is read-only and import requires Owner/Admin. Job/attempt/delivery uniqueness and transactional receipts defend against replay, racing attempts and response loss. Successful delivery identities cannot be recycled. Receipt fingerprints are sensitive metadata, not anonymization. No raw CSV/error row is stored in the ledger. No export exists; future exports need formula neutralization. No consent or communication permission is inferred from a contact channel.

Business activity contains bounded structured changes and an intentional human reopening reason. It is separate from security audit events, request logs and future agent traces. No automatic mutable contact snapshots are copied into history. Attribution URLs lose query/fragment/credentials, but even a URL path or human note can contain PII: users and future retention policy remain responsible for minimizing business content.

Cursor integrity binds verified user, organization, complete query/search mode/order and position; raw search terms are absent from cursor/log bodies. Prefix indexes improve candidate lookup without relaxing RLS; explicit broad substring queries can still time out and are a resource-exhaustion consideration. API limits remain per-process/IP and do not protect direct PostgREST traffic. A production gateway needs request/tenant quotas and monitoring.

CRM drafts are memory-only and scoped to verified identity/workspace. Revalidation suspends display; logout/user/role/revocation/workspace changes clear or isolate them. Epoch-bound late callbacks and aborted keyed reads prevent old-scope results resurfacing. Hard refresh can discard manual drafts; it does not roll back an already committed create. Durable import receipts recover results separately.

Application logs whitelist safe fields and omit raw bodies, query values, contact data and reason text. Database error rethrows discard failing-row DETAIL. Local PostgreSQL parameter logging on errors was verified disabled (`log_parameter_max_length_on_error=0`); operators must preserve that setting and review database/gateway logs before production. Database administrators, backups, runtime memory and encryption keys remain privileged boundaries. No retention purge, privacy erasure/export, MFA rollout, abuse gateway, production CSP, restore drill or compliance certification is delivered by Phase 02.
